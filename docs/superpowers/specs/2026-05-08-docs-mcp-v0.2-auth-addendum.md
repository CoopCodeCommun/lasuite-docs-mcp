# Spec v0.2 — Authentification utilisateur (addendum)

**Date :** 2026-05-08
**Statut :** Design en cours de validation
**Référence :** étend la [spec v0.1](2026-05-08-docs-mcp-design.md). Toutes les conventions, contraintes, et choix architecturaux de la v0.1 restent en vigueur sauf mention contraire ici.

---

## 1. Objectif

Permettre à l'agent IA de réaliser des opérations qui nécessitent une authentification utilisateur sur l'instance Docs cible : créer des documents (top-level et sous-documents), les renommer, les déplacer dans l'arborescence, les dupliquer, les supprimer, et lister les documents accessibles à l'utilisateur connecté (pas seulement les publics).

**Mécanisme d'auth retenu :** cookies de session Django + protection CSRF (le seul mécanisme exploitable par un client externe sur les instances Docs en production type `notes.liiib.re`, validé empiriquement). L'utilisateur copie deux valeurs depuis les DevTools de son navigateur, l'agent les enregistre via un tool dédié, le serveur MCP les utilise en mémoire pour la durée du process.

**Évolution de la configuration :** la v0.2 supprime la configuration obligatoire `DOCS_INSTANCE_URL`. L'instance est désormais détectée dynamiquement à partir des liens vers des documents que l'utilisateur partage avec l'agent (ex : `https://notes.liiib.re/docs/ccf11f43-.../`). Cela transforme `DOCS_INSTANCE_URL` d'une config statique en un état conversationnel détenu par le serveur MCP. Voir §10.

**Non-objectifs (hors v0.2) :**
- OIDC user flow PKCE complet (reporté à v0.3 si besoin émerge)
- Auto-import depuis Chrome/Firefox via lecture du SQLite (reporté à v0.3)
- Persistance disk des credentials (jamais — contrainte forte de sécurité)
- Création/édition d'accès collaboratifs (`/documents/{id}/accesses/`)
- Gestion des invitations
- Multi-instance simultanée (un seul `InstanceStore` à la fois — un switch implique de clear l'instance précédente)

## 2. Décisions actées (pré-spec)

Ces 4 questions ont été tranchées avec l'utilisateur en amont de la rédaction :

| Question | Réponse |
|---|---|
| Périmètre des tools | **Tout doit être possible** — création top-level, création sous-doc, déplacement, duplication, renommage, suppression, listing personnel |
| Cookie utilisé pour quels appels ? | **Seulement quand nécessaire** : la lecture publique reste anonyme (comportement v0.1 préservé). On ne demande le cookie que sur les ops qui en ont strictement besoin. |
| Comportement à l'expiration du cookie (12h) | **Retour `AUTH_REQUIRED`** : pas de détection proactive, on retourne l'erreur typée et l'agent demande de nouveaux credentials |
| Sécurité du cookie en mémoire | **Contrainte forte** : jamais loggé, jamais inclus dans les outputs de tools, jamais persisté disque |

## 3. Architecture

### 3.1. Nouveau module : `src/auth/credentials.ts`

Un singleton `CredentialsStore` qui détient les credentials en mémoire pour la durée du process.

```typescript
type SessionCredentials = {
  docs_sessionid: string;
  csrftoken: string;
};

class CredentialsStore {
  // Méthodes : set / get / clear / has
  // Stockage : variable privée du module, JAMAIS exportée directement
  // toString / inspect override : retournent "[CredentialsStore: <set|empty>]" sans valeur
}
```

Pourquoi un module dédié et pas juste une variable globale dans `server.ts` :
- **Une responsabilité par fichier** (convention v0.1)
- **Testabilité** : on peut mocker `CredentialsStore` dans les tests
- **Override `toString`/`inspect`** : impossible d'imprimer accidentellement les credentials via un `console.log` du store (cf. contrainte sécurité 4)

### 3.2. Modifications de modules existants

| Module | Changement |
|---|---|
| `src/docs/connection.ts` | `createDocsWebSocketClass(url)` devient `createDocsWebSocketClass(url, credentialsStore)`. Si `credentialsStore.has()` au moment de la connexion WS, le cookie `Cookie:` envoyé est `docs_sessionid=<vraie valeur>; csrftoken=<vraie valeur>` au lieu du dummy `docs_sessionid=anonymous-bot`. Sinon, comportement v0.1 inchangé. |
| `src/docs/client.ts` | Méthodes existantes `fetchDocumentMetadata`, `assertPublicEditor`, `listPublicDocuments` : inchangées (lecture publique reste anonyme). Nouvelles méthodes pour les ops d'écriture, qui exigent des credentials et lèvent `DocsError("AUTH_REQUIRED")` si absents. Le client REST construit alors les 4 headers : `Cookie`, `Content-Type`, `Referer` (dérivé de `DOCS_INSTANCE_URL`), `X-CSRFToken`. |
| `src/types.ts` | Nouveau code d'erreur : `AUTH_REQUIRED`. Ajouts à `DocsErrorCode`. |
| `src/server.ts` | Enregistre les nouveaux tools (cf. §4) et instancie `CredentialsStore` au démarrage. Format de l'erreur `AUTH_REQUIRED` inclut un message bilingual avec les instructions Chrome / Firefox pour récupérer les 2 cookies. |

### 3.3. Frontière de propagation des credentials

Les credentials sont **lus** uniquement par `connection.ts` et `client.ts` (les deux fichiers qui parlent au serveur Docs). Aucun autre module ne doit y avoir accès. Le `CredentialsStore` n'est passé qu'aux modules qui en ont besoin, jamais à `blocks.ts` ni à `session.ts` (qui n'en ont pas l'utilité — ils opèrent sur le `Y.Doc` déjà synchronisé).

## 4. Surface MCP — nouveaux tools

### 4.1. Tools d'authentification (2)

#### `set_session_credentials`

```ts
input: {
  docs_sessionid: string;     // valeur du cookie Django de session
  csrftoken: string;          // valeur du cookie CSRF Django
  instance_url?: string;      // ex: "https://notes.liiib.re" — optionnel,
                              // settle l'instance en même temps si fourni
                              // (cf. §10.5)
}
→ { ok: true }
```

Stocke les credentials dans `CredentialsStore`. Aucune validation côté MCP : le serveur ne pingeune pas l'instance pour vérifier. Si les credentials sont invalides, c'est la première op d'écriture qui retournera `DocsError("AUTH_REQUIRED")`. Cela évite un round-trip inutile et garde le store simple.

#### `clear_session_credentials`

```ts
input: {}
→ { ok: true }
```

Vide `CredentialsStore`. **Ne touche pas à `InstanceStore`** : on garde l'instance settled pour continuer à lire les docs publics anonymement. Pour switcher d'instance, il faut soit appeler à nouveau `set_session_credentials` avec un nouveau `instance_url`, soit passer un `doc_url` d'une autre instance (ce qui lèvera `INSTANCE_MISMATCH` — cf. §10.4).

### 4.2. Tools d'écriture (6)

Tous ces tools exigent :
1. **Une instance settled** (via env var `DOCS_INSTANCE_URL` au démarrage, via un précédent `doc_url` reçu, ou via `set_session_credentials.instance_url`). Si aucune instance settled, retourne `DocsError("INSTANCE_NOT_SET", ...)` (cf. §10.4).
2. **Des credentials valides**. Si `CredentialsStore.has() === false`, retourne `DocsError("AUTH_REQUIRED", <message_avec_instructions>)` sans toucher au réseau.

**Référence des documents : `doc_id` ou `doc_url` (cf. §10.3).** Toutes les signatures ci-dessous montrent `doc_id`, mais la spec accepte indifféremment `doc_url` (URL complète vers le doc) qui sera parsée pour extraire l'origine et l'UUID. Si `doc_url` est passé pour une instance différente de celle settled, retourne `INSTANCE_MISMATCH`.

#### `create_document`

```ts
input: {
  title: string;
  parent_id?: DocumentId | null;  // null/absent → top-level, sinon sous-doc
}
→ { id: DocumentId; title: string; depth: number; path: string; link_reach: string }
```

Si `parent_id` est null/absent, appelle `POST /api/v1.0/documents/`. Sinon, appelle `POST /api/v1.0/documents/{parent_id}/children/`. Un seul tool unifié plutôt que deux séparés (DRY).

#### `delete_document`

```ts
input: { doc_id: DocumentId; }
→ { ok: true }
```

Soft delete via `DELETE /api/v1.0/documents/{doc_id}/`. La cascade vers les sous-docs est gérée côté Docs (validé empiriquement : `204 No Content` sur le parent supprime aussi les enfants).

#### `move_document`

```ts
input: {
  doc_id: DocumentId;
  target_parent_id: DocumentId;
  position: "first-child" | "last-child" | "left" | "right";  // selon enums.MoveNodePositionChoices
}
→ { ok: true }
```

Re-parente via `POST /api/v1.0/documents/{doc_id}/move/`.

#### `duplicate_document`

```ts
input: {
  doc_id: DocumentId;
  with_accesses?: boolean;  // défaut false
}
→ { id: DocumentId; title: string; }
```

Duplique via `POST /api/v1.0/documents/{doc_id}/duplicate/`.

#### `update_document_title`

```ts
input: { doc_id: DocumentId; title: string; }
→ { ok: true }
```

Renomme via `PATCH /api/v1.0/documents/{doc_id}/` avec `{title}`. Tool focalisé titre uniquement (pas de modification d'autres champs métadonnées en v0.2 — YAGNI).

#### `list_my_documents`

```ts
input: {
  page?: number;  // défaut 1
  page_size?: number;  // défaut 20, max 100
}
→ {
    count: number;
    results: Array<DocumentSummary>;  // mêmes champs que list_documents, mais inclut les docs privés du user
  }
```

Liste les docs accessibles via `GET /api/v1.0/documents/`. Différent de `list_documents` v0.1 qui filtrait sur `link_reach: public` côté client. Ici on retourne tout ce que l'utilisateur peut voir (privés + publics + partagés).

### 4.3. Surface totale après v0.2

| | v0.1 | v0.2 |
|---|---|---|
| Lecture | `list_documents`, `read_document`, `get_document_metadata` | + `list_my_documents` |
| Édition de contenu | `insert_block`, `update_block`, `delete_block` | (inchangés) |
| Auth | — | `set_session_credentials`, `clear_session_credentials` |
| Gestion arborescence | — | `create_document`, `delete_document`, `move_document`, `duplicate_document`, `update_document_title` |
| **Total** | 6 tools | **14 tools** |

## 5. Flux d'authentification

Séquence type quand l'utilisateur demande une opération d'écriture pour la première fois :

```
USER  → "Crée un nouveau document s'appelant 'Réunion du 15 mai'"

Agent → MCP: create_document({title: "Réunion du 15 mai"})
MCP   → CredentialsStore.has() === false
        → retourne DocsError("AUTH_REQUIRED", <message complet>)

Agent (lit le message d'erreur, le reformule pour l'utilisateur)
      ↓
USER  ← "Cette opération demande tes credentials Docs. Voici comment les
         récupérer :
         [instructions Chrome / Firefox]
         Une fois les 2 valeurs copiées, donne-les moi."

USER  → "docs_sessionid=abc123 csrftoken=def456"

Agent → MCP: set_session_credentials({docs_sessionid: "abc123", csrftoken: "def456"})
MCP   → stocke en mémoire
        → retourne {ok: true}

Agent → MCP: create_document({title: "Réunion du 15 mai"})  // retry
MCP   → CredentialsStore.has() === true
        → POST /api/v1.0/documents/ avec les 4 headers
        → retourne {id: "...", title: "Réunion du 15 mai", ...}

USER  ← "Document créé. ID: ..."
```

**Cas du cookie expiré** : à ~12h après login, le serveur Docs commence à retourner 401 / 403. Le client REST interprète cette réponse comme `AUTH_REQUIRED` (avec un message légèrement différent : « les credentials ont expiré, recolle les nouvelles valeurs »). L'agent demande à l'utilisateur de récupérer un nouveau couple cookies, qui remplace l'ancien dans le `CredentialsStore`.

## 6. Message d'erreur `AUTH_REQUIRED`

Le payload de l'erreur a la forme suivante (renvoyée à l'agent dans le `content[].text` JSON) :

```json
{
  "code": "AUTH_REQUIRED",
  "message": "Cette opération nécessite un cookie de session valide. Pour récupérer tes 2 cookies sur l'instance Docs cible :\n\n== Chrome / Edge / Brave (Chromium) ==\n1. Connecte-toi à l'instance Docs dans ton navigateur (par exemple https://notes.liiib.re).\n2. Ouvre les DevTools : F12, ou Ctrl+Shift+I (Windows/Linux), ou Cmd+Option+I (macOS).\n3. Onglet \"Application\" → menu de gauche → \"Cookies\" → URL de ton instance.\n4. Repère les 2 lignes : 'docs_sessionid' et 'csrftoken'. Pour chacune, clic droit sur la cellule \"Value\" → \"Copy value\".\n\n== Firefox ==\n1. Connecte-toi à l'instance Docs dans ton navigateur.\n2. Ouvre les DevTools : F12, ou Ctrl+Shift+I (Windows/Linux), ou Cmd+Option+I (macOS).\n3. Onglet \"Stockage\" (ou \"Storage\" en anglais).\n4. Menu de gauche → \"Cookies\" → URL de ton instance.\n5. Repère les 2 lignes 'docs_sessionid' et 'csrftoken', clic droit dessus → \"Copier la valeur\".\n\nNote : 'docs_sessionid' est marqué HttpOnly, invisible depuis la console JavaScript — il faut passer par les DevTools.\n\nLe couple de cookies expire ~12h après login. Si l'opération échoue plus tard avec la même erreur, c'est qu'il faut récupérer un nouveau couple.\n\nUne fois les 2 valeurs copiées, donne-les moi et j'enregistrerai pour la durée de la session MCP. Elles ne sont ni écrites sur disque ni renvoyées dans les réponses de tools.",
  "instructions_browsers": ["chrome", "firefox"]
}
```

L'agent est libre de reformater / résumer le message pour l'afficher à l'utilisateur final, mais l'information complète y est.

## 7. Contraintes de sécurité (forte)

Les contraintes suivantes sont **non-négociables** et doivent être vérifiées explicitement dans le code et dans les revues :

1. **Jamais loggé** : aucun `console.log`, `logger.info`, `process.stdout.write`, etc. ne doit recevoir une valeur de cookie. Le `CredentialsStore` override `toString` et `Symbol.for("nodejs.util.inspect.custom")` pour retourner `"[CredentialsStore: <set|empty>]"` même si on essaie de l'imprimer accidentellement.

2. **Jamais inclus dans les outputs de tools** : aucune réponse MCP ne doit contenir un cookie. Les codes d'erreur MCP générés par les tools d'écriture après échec (par exemple `AUTH_REQUIRED` après cookie expiré) ne doivent contenir que des messages génériques, pas la valeur du cookie qui a échoué.

3. **Jamais persisté disque** : pas d'écriture dans un fichier, pas de cache disque, pas de logs. Le store vit en RAM dans le process MCP. Si le process s'arrête, les credentials sont perdus — c'est volontaire.

4. **Jamais transmis à un autre tool que `connection.ts` / `client.ts`** : les modules `blocks.ts` et `session.ts` n'ont pas connaissance des credentials. Le `CredentialsStore` n'est passé qu'à `connection.ts` (au constructeur de `DocsWebSocket`) et à `client.ts` (au constructeur de `DocsRestClient`).

5. **Filtrage par domaine** : si une future v0.3 ajoute l'auto-import depuis Chrome/Firefox, elle filtrera strictement par le hostname dérivé de `DOCS_INSTANCE_URL` et ne touchera pas aux cookies d'autres sites. Hors scope v0.2 mais à mémoriser.

6. **Tool `clear_session_credentials` exposé** : l'utilisateur a un moyen explicite et programmatique de purger les credentials sans tuer le process.

## 8. Tests

### 8.1. Tests unitaires (vitest, sans réseau)

- `CredentialsStore` :
  - `set` puis `get` retourne les credentials
  - `clear` après `set` retourne au state `empty`
  - `has` retourne `true` après `set`, `false` initialement et après `clear`
  - `toString` et `inspect` retournent `"[CredentialsStore: ...]"` sans jamais inclure une vraie valeur — y compris quand le store est rempli
  - `JSON.stringify` du store : ne fuit pas la valeur (override de `toJSON` ou type qui ne sérialise pas)

### 8.2. Tests d'intégration manuels

Étendre `tests/integration.test.ts` (ou créer un `tests/integration-auth.test.ts` dédié) :
- Set credentials avec des valeurs en variables d'env (`DOCS_INTEGRATION_SESSIONID`, `DOCS_INTEGRATION_CSRFTOKEN`)
- Créer un doc top-level
- Créer un sous-doc
- Le renommer
- Le déplacer (sous un autre parent ou en racine)
- Le dupliquer
- Lister `list_my_documents` et vérifier que les nouveaux docs apparaissent
- Tout supprimer (cleanup garanti même en cas d'échec)

Idempotent : aucun doc ne doit subsister après la fin du test.

## 10. Détection dynamique de l'instance Docs

### 10.1. Motivation

En v0.1, l'instance cible était figée au démarrage via `DOCS_INSTANCE_URL` (avec un défaut `https://notes.liiib.re`). Cela implique :

- L'utilisateur doit configurer une variable d'environnement avant le premier usage.
- Pour utiliser le MCP avec une autre instance Docs, il faut redémarrer le serveur MCP avec une nouvelle config.
- Aucune protection contre la confusion : l'utilisateur peut passer à l'agent un lien vers une instance différente de celle configurée — le MCP utilisera silencieusement l'instance configurée et échouera de manière obscure (404 sur le doc_id) sans signaler le mismatch.

En v0.2, on observe que les utilisateurs partagent naturellement des **liens complets** vers des documents (`https://notes.liiib.re/docs/ccf11f43-a52e-48c6-bcb2-1858f8a42256/`). Ces liens contiennent **les deux informations** dont le MCP a besoin : l'origine de l'instance (host) et l'UUID du document. Plutôt que demander à l'utilisateur de séparer ces infos manuellement, le MCP peut les extraire et adapter son contexte.

### 10.2. `InstanceStore` (parallèle au `CredentialsStore`)

Un nouveau singleton `src/auth/instance.ts` détient l'instance "active" pour la session :

```typescript
type DocsInstance = {
  origin: string;     // ex: "https://notes.liiib.re"
  // pas de host stocké séparément, dériver via new URL(origin).host
};

class InstanceStore {
  // Méthodes : set / get / clear / has / matches(url)
  // Init : si DOCS_INSTANCE_URL est dans process.env, set au démarrage
  // matches(url): true si l'origin de l'URL correspond à l'instance active
}
```

### 10.3. Format des arguments de tools : `doc_id` ou `doc_url`

Tous les tools qui prenaient `doc_id` en v0.1 acceptent désormais **soit** `doc_id` (UUID nu), **soit** `doc_url` (URL complète). Validation côté zod :

```ts
const documentReferenceSchema = z.union([
  z.object({ doc_id: z.string().uuid() }),
  z.object({ doc_url: z.string().url() }),
]);
```

Comportement uniforme :
- Si `doc_url` est passé : extraire l'origine (ex: `https://notes.liiib.re`) et l'UUID depuis le path (regex sur `/docs/([0-9a-f-]{36})`).
- Si `doc_id` est passé : utiliser l'instance active de `InstanceStore`. Si aucune instance n'est settled, retourner `INSTANCE_NOT_SET`.

### 10.4. Comportement de l'instance "active"

| Situation | Comportement |
|---|---|
| `DOCS_INSTANCE_URL` env var définie au démarrage | `InstanceStore` initialisé avec cette valeur. Toutes les ops fonctionnent comme en v0.1. |
| Pas d'env var, premier `doc_url` passé à un tool | Extraction de l'origine, settle dans `InstanceStore`. Toutes les ops suivantes utilisent cette instance. |
| Tool appelé avec `doc_id` mais aucune instance settled | Retourne `DocsError("INSTANCE_NOT_SET", "Pour cette opération, je dois savoir sur quelle instance Docs travailler. Passe-moi un lien vers un document (ex: https://notes.liiib.re/docs/<UUID>/) ou redémarre avec DOCS_INSTANCE_URL.")`. |
| Tool appelé avec `doc_url` dont l'origine diffère de l'instance settled | Retourne `DocsError("INSTANCE_MISMATCH", "Tu m'as donné un lien vers <X>, mais je suis actuellement connecté à <Y>. Pour switcher, appelle clear_session_credentials puis recommence — je vais oublier les credentials de l'instance précédente avant de me reconnecter à la nouvelle.")`. **Le serveur ne switche jamais silencieusement** : c'est un acte volontaire de l'utilisateur. |

### 10.5. Tools sans `doc_id` ni `doc_url`

Certains tools n'opèrent sur aucun doc spécifique :
- `list_documents` (v0.1)
- `list_my_documents` (v0.2)
- `create_document` quand `parent_id` est absent (création top-level)
- `set_session_credentials` (v0.2)

Ces tools requièrent qu'une instance soit settled (via env var ou via un précédent appel avec `doc_url`). S'ils sont appelés alors qu'aucune instance n'est settled, ils retournent `INSTANCE_NOT_SET` avec un message qui guide l'utilisateur vers le partage d'un lien.

Pour `set_session_credentials` : le tool ajoute un champ optionnel `instance_url` qui permet de settler l'instance en même temps :

```ts
set_session_credentials({
  docs_sessionid: string;
  csrftoken: string;
  instance_url?: string;  // ex: "https://notes.liiib.re"
})
```

Cela permet à l'utilisateur de fournir tout en un seul appel quand il colle un cookie pour une nouvelle instance.

### 10.6. Lien entre instance et credentials

Les credentials sont **liés à l'instance active**. Conséquences :

- Si on appelle `clear_session_credentials`, on clear aussi l'instance ? **Non, on garde l'instance** — l'utilisateur peut vouloir simplement se "déconnecter" d'un compte sur une instance et continuer à lire ses docs publics.
- Si on switche d'instance (`INSTANCE_MISMATCH` levé, l'utilisateur fait un `clear_session_credentials` puis repasse un nouveau `doc_url`), les credentials sont déjà clearées par le précédent appel — c'est cohérent.
- Si on essaie de set credentials pour une instance différente de celle settled, le `instance_url` paramètre permet de switcher proprement (il fait implicitement `clearInstance` + `setInstance(instance_url)` + `setCredentials(...)`).

### 10.7. Sécurité

Une nouvelle contrainte forte s'ajoute aux 6 contraintes existantes :

7. **Pas de mélange d'instances** : si l'instance settled est X et qu'un tool reçoit une URL pour Y, le serveur n'envoie **jamais** les credentials (qui appartiennent à X) vers Y. Le check est fait dans `connection.ts` et `client.ts` au moment de construire la requête : si la base URL de la requête diffère de l'instance settled, abort avec `INSTANCE_MISMATCH`.

### 10.8. Exemple de séquence

```
USER  → "Lis le doc https://notes.liiib.re/docs/ccf11f43-.../"

Agent → MCP: read_document({ doc_url: "https://notes.liiib.re/docs/ccf11f43-.../" })
MCP   → InstanceStore.has() === false
        → extrait origin "https://notes.liiib.re" + uuid "ccf11f43-..."
        → InstanceStore.set("https://notes.liiib.re")
        → procède à la lecture (anonyme, doc public)
        → retourne le contenu

USER  → "Crée un sous-doc 'Notes' dedans"

Agent → MCP: create_document({ title: "Notes", parent_id: "ccf11f43-..." })
MCP   → InstanceStore.has() === true (settled précédemment)
        → CredentialsStore.has() === false
        → retourne AUTH_REQUIRED avec instructions DevTools

[utilisateur copie les 2 cookies, les colle]

Agent → MCP: set_session_credentials({ docs_sessionid: "...", csrftoken: "..." })
MCP   → CredentialsStore.set(...) — pas d'instance_url car déjà settled
        → retourne {ok: true}

Agent → MCP: create_document({ title: "Notes", parent_id: "ccf11f43-..." })
MCP   → tout est en place
```

## 11. Critères de succès

La v0.2 est livrable quand :

**Auth & credentials :**
1. Le tool `set_session_credentials` accepte 2 strings (et un `instance_url` optionnel) et les stocke en `CredentialsStore`.
2. Le tool `clear_session_credentials` purge `CredentialsStore` mais conserve `InstanceStore`.
3. Sans `set_session_credentials` préalable, tous les tools d'écriture retournent `AUTH_REQUIRED` avec un message contenant les instructions Chrome ET Firefox.
4. Cookie expiré : la prochaine op retourne `AUTH_REQUIRED` (variant « expired »).
5. Tests unitaires : `CredentialsStore` ne fuit jamais sa valeur via `toString`, `inspect`, `JSON.stringify`, ou un `console.log` accidentel.

**Tools d'écriture :**
6. `create_document(title)` (sans `parent_id`) crée un doc top-level chez l'utilisateur authentifié.
7. `create_document(title, parent_id)` crée un sous-doc dans l'arborescence.
8. `delete_document` supprime un doc et ses enfants en cascade.
9. `move_document` déplace un doc dans l'arbre.
10. `duplicate_document` duplique un doc.
11. `update_document_title` renomme un doc.
12. `list_my_documents` retourne les docs accessibles au user (privés + publics).

**Détection d'instance :**
13. Au démarrage sans `DOCS_INSTANCE_URL` env var, `InstanceStore` est vide. Le premier tool appelé sans `doc_url` retourne `INSTANCE_NOT_SET`.
14. Le premier `doc_url` passé à un tool extrait l'origine et settle `InstanceStore`. Les ops suivantes utilisent cette instance.
15. Avec `DOCS_INSTANCE_URL` env var définie, `InstanceStore` est settled au démarrage (compat v0.1 préservée).
16. Tool appelé avec `doc_url` d'une instance différente de celle settled retourne `INSTANCE_MISMATCH` — pas de switch silencieux.
17. Tools acceptent indifféremment `doc_id` ou `doc_url` ; les deux mènent au même résultat quand l'instance est cohérente.

**Préservation de la v0.1 :**
18. Lecture publique (`list_documents`, `read_document`, `get_document_metadata`, `insert_block`, `update_block`, `delete_block`) reste fonctionnelle sans credentials (comportement v0.1 préservé).
19. Test d'intégration v0.1 reste vert.

**Sécurité :**
20. `connection.ts` et `client.ts` n'envoient jamais les credentials vers une URL dont l'origine diffère de `InstanceStore.get()`.

**Tests & doc :**
21. Test d'intégration manuel v0.2 passe (set credentials → créer top-level → sous-doc → renommer → move → dupliquer → list → cleanup) avec credentials valides.
